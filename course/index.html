What Happens When You Tap

ChildTaskTracker in one sentence, then one tap traced all the way down.

The app, in plain terms

ChildTaskTracker is a chore-and-rewards app for families. A kid marks chores done, a parent approves them, and points build toward rewards the parent already agreed to.

✅
Tasks

The kid's daily to-do list — tap to mark something done.

🎁
Rewards

A shelf of parent-set prizes, priced in points.

📈
Progress

Streaks, points, and a plain-English weekly recap.

Imagine you're the kid

It's morning. You brushed your teeth. You open the app and tap the little circle next to "Brush teeth." That single tap is the doorbell of this whole system — everything else in this course is what happens after someone rings it.

In programming, that tap is called an event. Somewhere in the code, something is sitting and listening for exactly this doorbell.

Here's the listener, catching your tap

Every button in the app is tagged with a label like data-action="complete-task". One single piece of code listens for clicks anywhere on the page and checks that label to decide what to do — instead of writing a separate listener for every single button.

CODE — app.js 
document.addEventListener('click', async (e) => {
  const target = e.target.closest('[data-action]');
  if (!target) return;
  const action = target.dataset.action;
  if (action === 'complete-task') { spawnConfetti(...); markTaskDone(target.dataset.task); return; }
PLAIN ENGLISH

Listen for any click, anywhere on the whole page.

Walk up from wherever was clicked until we find something tagged with a job to do.

If nothing nearby has a job, ignore the click entirely.

Read the job's name off the tag.

If the job is "mark a task complete," celebrate and run markTaskDone().

💡
Key insight

This pattern is called event delegation. One listener handles every button in the app — add a hundred new buttons tomorrow and this code doesn't change.

Meet the Cast

Four files play four very different roles — like the crew behind a small play.

Four files, four jobs

Think of the app like a small play. One file is the stage. One is the costumes. One is the cast and script, doing all the acting. One is a guest consultant who only shows up when specifically called.

index.htmlThe stage — an empty shell the other files fill in
styles.cssThe costumes and set design — every color, shape, spacing rule
app.jsThe cast and script — state, rendering, every button's behavior
ai.jsA guest consultant — called in only for AI suggestions, with a stand-in ready if they don't show

The script everyone reads from

Nearly every actor in app.js reads from and writes to one shared object called STATE. It's the single source of truth — every child, task, and point balance lives here, and nowhere else.

🧒

children

Name, age, avatar, current points — one entry per kid.

✅

tasks & completions

What's assigned, and every time it was marked done, approved, or rejected.

🎁

rewards & redemptions

The prize catalog, and every request to cash points in.

📒

pointsLedger & notifications

Every point earned or spent, and every alert sent to a parent.

Where STATE actually starts

The very first lines of the app build this object. Nothing fancy — just a plain JavaScript object with empty lists waiting to be filled in.

CODE — app.js 
const state = {
  clock: { simulatedNowMs: now, simulatedDate: today },
  parentNames: { A: 'Parent A', B: 'Parent B' },
  children: [], tasks: [], completions: [], rewards: [], redemptions: [], pointsLedger: [], notifications: [],
};
PLAIN ENGLISH

Start building the app's one and only object.

Remember what "today" is — more on this trick in Module 5.

Give each parent a default display name, which Settings can change later.

Seven empty lists, each one ready to hold a different kind of record.

Every list here is a array — an ordered list the app can search, filter, and add to.

Who's allowed to change the script

Reading STATE happens everywhere, but changing it only happens through a small set of named functions — never by reaching in and editing it directly from just anywhere.

✏️
Mutation functions

markTaskDone(), approveCompletion(), addLedger() — the only code allowed to change STATE.

🖼️
render()

Reads STATE and rebuilds the on-screen HTML — never changes anything itself.

💾
saveState() / loadState()

The only two functions that touch the browser's long-term storage.

💡
Good to know

Keeping "things that change data" and "things that display data" separate is a core software idea. It means you always know exactly where to look when something's wrong: is the data wrong, or is the display of it wrong?

The whiteboard, wiped and redrawn

render() doesn't figure out what changed and tweak just that piece. It throws away the entire screen and rebuilds it from STATE, every single time — like a whiteboard that gets wiped clean and redrawn from memory after every edit, rather than erasing just one word.

💡
Key insight

Frameworks like React exist specifically to avoid this — they compare old and new versions and only touch what changed, called diffing. This app skips that entirely: no framework, no build step, just a template rebuilt from scratch. Slower in theory, invisible in practice at this scale, and radically simpler to reason about.

The notebook that survives closing the tab

Browsers give every website a small private notebook called localStorage. Close the two functions that are the app's only connection to it:

CODE — app.js 
function loadState() {
  try {
    const raw = localStorage.getItem(STORAGE_KEY);
    return raw ? JSON.parse(raw) : null;
  } catch { return null; }
}
function saveState() {
  try { localStorage.setItem(STORAGE_KEY, JSON.stringify(STATE)); } catch {}
}
PLAIN ENGLISH

On startup, try to read whatever was saved before.

Turn the saved text back into a real JavaScript object — localStorage can only hold text.

If nothing's saved yet, say so honestly instead of crashing.

Every time STATE changes...

...turn the whole thing into text and save it — quietly failing instead of crashing if storage is full or blocked.

Calling In Outside Help

The one place this app leaves the browser — and what happens if that call doesn't answer.

One phone line to the outside world

Everything you've seen so far — every list, every point, every approval — happens entirely inside your browser. There's exactly one thing that ever leaves it: an optional call to OpenAI, for features like "suggest a reward" or "write my weekly recap."

Think of it like a small shop with one landline that only rings out to a single specialist — everything else the shop handles itself, in-house.

The call itself

No backend server sits between the browser and OpenAI. The browser dials directly, using a key the parent typed into Settings.

The AI doesn't get to invent a reward

The instructions sent to OpenAI don't just ask for a suggestion — they force it to pick from the parent's own list. Look closely at the very first sentence of the instructions below.

CODE — ai.js 
{ role: 'system', content: 'You recommend a reward for a child from a
  PARENT-APPROVED list only. You must pick the "id" of exactly
  one item from the provided catalog — never invent a new reward,

PLAIN ENGLISH

This is a system prompt — the AI's rulebook for this one task.

The very first sentence is a hard boundary: only rewards the parent already added.

Spelled out again, explicitly, so there's no ambiguity: no inventing anything.

And it must answer in a strict, predictable data format the code can trust.

Even if the answer comes back malformed, the code double-checks: const match = active.find(r => r.id === parsed.rewardId); if (!match) throw new Error(...) — an AI reply that names a reward that doesn't exist gets rejected and falls through to the same rule-based fallback as a network error.

The Clever Tricks

Two small pieces of logic that make a 24-hour wait and a forgiving streak both testable in seconds.

The problem with "wait 24 hours"

If a parent doesn't approve a task, it should auto-approve after a day — so a busy evening never costs a kid their streak. But how do you test that without actually waiting a full day, every single time?

The trick: the app never asks the real computer clock what time it is. It keeps its own pretend clock in STATE, and a button in Settings can fast-forward it — like a remote control for time itself.

Fast-forwarding a day

CODE — app.js 
function advanceOneDay() {
  STATE.clock.simulatedNowMs += 86400000;
  STATE.clock.simulatedDate = isoDate(new Date(STATE.clock.simulatedNowMs));
  checkAutoApprovals();
  saveState();
  showToast('⏩ A new day has begun!');
  render();
}
PLAIN ENGLISH

Add exactly one day's worth of milliseconds — 86,400,000 of them — to the pretend clock.

Update the human-readable date to match.

Immediately check: does anything need to auto-approve now that a day has "passed"?

Save, celebrate with a toast, and redraw the screen.

💡
Good to know

Every timestamp in the app — when a task was marked done, when a redemption was requested — is measured against this pretend clock, not the real one. That's what makes the whole demo deterministic and repeatable.

The check that actually approves things

CODE — app.js 
function checkAutoApprovals() {
  let changed = false;
  STATE.completions.filter(c => c.status === 'pending').forEach(c => {
    if (nowMs() - c.markedAtMs >= 86400000) { approveCompletion(c.id, 'auto'); changed = true; }
  });
  if (changed) saveState();
}
PLAIN ENGLISH

Look at every task still waiting on a parent.

For each one: has a full day passed since it was marked done?

If yes, approve it automatically and remember that something changed.

Only bother saving if anything actually got auto-approved.

A streak survives one bad day

Miss a single day and a real streak shouldn't just vanish — that's punishing, and it's how habit apps lose people. This one forgives exactly one missed day before it resets, like a library that waives your fee once but not twice.

CODE — app.js 
let streak = 0, forgiven = false, cursor = addDays(todayStr(), -1), guard = 0;
while (guard++ < 90) {
  const due = tasksForChild(childId).filter(t => isTaskDueOn(t, cursor));
  if (due.length > 0) {
    const allDone = due.every(t => {
      const c = findCompletion(t.id, cursor);
      return c && (c.status === 'approved' || c.status === 'auto_approved');
    });
    if (allDone) streak++;
    else if (!forgiven) forgiven = true;
    else break;
  }
  cursor = addDays(cursor, -1);
}
PLAIN ENGLISH

Start counting from yesterday, with no forgiveness spent yet.

Walk backward day by day, up to 90 days, so this can never run forever.

Only count a day if the kid actually had tasks due on it.

Were every one of those tasks approved?

If yes: the streak grows by one.

If no, and forgiveness hasn't been used yet: spend it, and keep going.

If no, and forgiveness is already spent: stop counting — the streak ends here.

Step one more day into the past and repeat.

A loop walking backward through the calendar, one forgiven flag, one break. That's the entire streak-forgiveness feature.

When It Broke

Two real bugs from this exact app, and the debugging instinct each one teaches.

This actually happened

Everything you're about to see is a real bug that shipped to the live app before it was caught — not a made-up example. Debugging intuition comes from real breakage, so here it is.

Spot the bug

This is (almost) the real code for every popup in the app. Every button inside it — Save, Send, Cancel — stopped working the moment this line shipped. Click the line you think is responsible.

Find the bug:

1function modalConfirmRedeem(reward) {
2 return `<div class="modal" onclick="event.stopPropagation()">
3 <h3>Redeem ${reward.title}?</h3>
4 <button data-action="confirm-redeem" data-reward="${reward.id}">Send request</button>
5 </div>`;
6}

Why this one line broke everything

Remember Module 1's event delegation — one listener on document catches every click in the app by letting it "bubble" up from wherever you clicked. The line onclick="event.stopPropagation()" does exactly what it says: it stops that bubble from ever reaching document.

The button's click still fired. It just never got heard.

⚠️
Common mistake

The line looked defensive, not dangerous — a common instinct is "stop this click from closing the popup underneath it." But event delegation means every button's job depends on that same click reaching document. Stopping it anywhere stops it for everything nested inside.

A second bug: the router that wasn't broken

Scenario

An automated testing tool changed the page's address to a new screen. The screen never updated — it looked exactly like Module 3's router was broken. But real users clicking real links saw it work perfectly every time. What's actually going on?

What both bugs teach

🖱️

Click-test, don't just read

The stopPropagation bug was invisible in the code review — it only showed up the moment someone actually clicked "Save."

🧭

Match the real path

Testing tools can take shortcuts real users never take. If a bug only shows up in one specific tool, suspect the tool before the app.

📡

Caches hide your fixes

A CDN can keep serving an old file for minutes after you've pushed a real fix — confirm with the actual bytes, not just "I pushed it."
